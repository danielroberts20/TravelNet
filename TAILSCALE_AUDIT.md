## 2. Genuine dependency risks if Tailscale is removed

**Watchdog's entire automated recovery ladder has no fallback path.**
Per `DOCS/WATCHDOG.md` and `codex/infrastructure/watchdog-escalation.md`, all three of the Watchdog's SSH-triggered recovery actions (restart containers at 5 failures, rebuild at 7, graceful reboot at 10) SSH to the TravelNet Pi over its Tailscale hostname, using a key with `StrictHostKeyChecking=no` and no LAN-IP fallback coded anywhere in `actions.py`. The *documented* LAN fallback (`codex/recovery/tailscale-recovery.md`) is a manual, human-executed procedure ("SSH into the Watchdog Pi, then SSH the TravelNet Pi on the LAN") — it is not something the automated escalation ladder itself can do. **If Tailscale is the only transport the Watchdog's code uses for SSH, removing Tailscale without giving the Watchdog an alternative transport (LAN IP, or a Cloudflare Access-fronted SSH/API path) breaks the single most important self-healing mechanism in the whole system**, silently, at the exact moment (Pi has crashed/lost network) it's needed most.

**Watchdog's own health signal (`tailscale_ok`) has no replacement wired up yet.**
`travelnet_healthy = tailscale_ok AND api_ok` (DOCS/WATCHDOG.md §2) means the Watchdog's core health determination is *structurally* tied to a Tailscale ping succeeding. `check_cloudflare()` exists per `watchdog-escalation.md`'s escalation doc description but per the Departure Audit (`DOCS/DEPARTURE_AUDIT.md` §3.3/3.4), "the Watchdog checks Tailscale, not the public path" is called out as an *existing* known gap even today — the Cloudflare check is a monitor-only signal, not (yet) part of the `travelnet_healthy` boolean that drives escalation. Migrating away from Tailscale means this boolean's primary input disappears and must be redesigned, not just relabelled.

**The Watchdog's TLS trust for its own API health check is pinned to the Tailscale-issued cert.**
`check_api()` calls `verify=CERT_PATH`, and per `update_timezone.py`'s managed cron jobs, the file at `CERT_PATH` is refreshed monthly by `tailscale cert` and scp'd to the Watchdog over Tailscale itself. This is a circular dependency: the Watchdog's ability to *verify* TravelNet's health depends on a certificate whose renewal and distribution mechanism *is* Tailscale. Any migration needs a non-Tailscale-distributed cert (or to trust the existing `api.travelnet.dev` Let's Encrypt cert instead, which is already fetched via a wholly separate certbot/Cloudflare-DNS mechanism — see §3).

**Trevor's compute story (Ollama + Remote-PC SSH) defaults entirely to Tailscale hostnames**, with no code-level fallback (`Trevor/.env.example`, `server/app/compute/ssh.py`). Unlike the TravelNet↔Trevor hop (which the code already routes via the Docker service name, per the comment in `Trevor/app/config.py:35`), the PC-facing hops have no such pattern in place yet.

**The frontend (Dashboard) has two build-time-baked Tailscale URLs** (Watchdog link, Prefect UI link — findings #9/#11/#12). These aren't config-driven, so a source change + `npm run build` + Dashboard image rebuild is required, not just an env var flip.

**Nothing here suggests uploads/data-collection are at risk.** Overland, iOS Shortcuts, and Health Auto Export all go through `api.travelnet.dev` via the Cloudflare Tunnel already, independent of Tailscale entirely (confirmed by `codex/recovery/cloudflare-tunnel.md`'s "What breaks and what doesn't" table). The blast radius of a Tailscale removal is entirely confined to: (a) Dashboard/admin access, (b) Watchdog's automated recovery + health-check TLS trust, (c) Prefect UI access, (d) Trevor's Ollama/Remote-PC compute path, (e) the cert-renewal cron chain.

## 3. What's already Cloudflare-native today (the mirror to build from)

- **`api.travelnet.dev`** is served through an outbound **Cloudflare Tunnel** (`cloudflared`, systemd service, config at `/etc/cloudflared/config.yml`, tunnel named `travelnet`) — no port-forwarding, no public IP exposure. Documented end-to-end in `codex/infrastructure/cloudflare-setup.md` and `codex/recovery/cloudflare-tunnel.md`, including restart/troubleshooting steps and a "what breaks and what doesn't" table.
- **TLS for `api.travelnet.dev`** is handled by a wholly separate, already-working chain: `certbot renew` (DNS-01 via `certbot-dns-cloudflare`) → copies `fullchain.pem` into the same `Dashboard/certs/` directory nginx mounts → `docker restart travelnet-nginx`. This is the exact monthly-cron pattern (see `update_timezone.py`, findings #15) that a Dashboard-over-Cloudflare-Access migration could mirror for its own hostname, swapping `tailscale cert` for a second certbot invocation or a Cloudflare Origin CA cert.
- **Cloudflare R2** already handles offsite, `age`-encrypted DB backups via `rclone`, entirely independent of Tailscale, with a documented (though per the Departure Audit, untested) restore path.
- **Cloudflare Pages** already hosts two fully Tailscale-independent public properties (`travelnet.dev` demo site, `docs.travelnet.dev` Jekyll docs), auto-deploying from GitHub on push — proof the team is already comfortable with the Cloudflare deploy model for anything internet-facing.
- **DNS** for `travelnet.dev` is already in Cloudflare, with `api.travelnet.dev` as a CNAME to the Tunnel — adding a `dashboard.travelnet.dev` (or similar) hostname behind Cloudflare Access would be additive, not a new DNS provider or account.
- **The middleware pattern itself is reusable**: `PublicPathFilterMiddleware`'s Host-header-based routing (`api.travelnet.dev` vs `public.travelnet.dev`) is exactly the shape of check a Cloudflare Access-fronted Dashboard hostname would need — a third branch keyed on the new hostname, rather than a new mechanism.
